Questions

Common questions

  • What counts as one workflow? One repeated job with a start and a finish — a feed that has to land in a sheet, images that have to be filed and resized, a digest that has to go out. If two jobs depend on each other's output, price it as a pipeline.
  • Which tool will you use? n8n, Make or Zapier when they fit and you can keep maintaining them; a small script with a schedule when the job needs logic they cannot express. We say which and why in the proposal, not after the build.
  • What happens when it breaks? It tells you, in the channel you already read, with the line that failed. A run that reports success while doing nothing is the expensive kind of failure, so failure detection is part of the build, not an extra.
The part most builds get wrong

"Successful" is not the same as correct

Automation tools will happily record a run as a success while the actual work failed: a field silently empty, a page that returned a login wall, a file that saved with the wrong name. It is a configuration choice, and a rushed build usually gets it wrong.

So the checks are part of the build, not an upgrade: a row count compared against the source, a rule for what "looks wrong", and an alert to the channel you already read with the line that failed.

What that means in the repo

  • A run log you can open and read without us
  • Retries, and a clear stop after the last one
  • Failure alerts that name the step, rather than a bare "job failed"
  • Idempotent steps, so a re-run does not double a record
  • A dry-run mode against a copy before it touches live data

Every one of these is verifiable in the handover: you can re-run it, break it on purpose, and watch the alert arrive.
